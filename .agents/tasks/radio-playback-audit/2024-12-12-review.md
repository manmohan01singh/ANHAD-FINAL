# Radio playback reliability engineering

Phase 3 implements diagnostic logging, live stream EOF recovery, position watchdog, and reconnection feedback. The changes target Darbar Sahib stream failures and virtual broadcast interruptions through detection, retry, and user feedback mechanisms.

**Watch for:** Position watchdog runs forever without cleanup (confirmed), retry loop after 6 failures continues indefinitely on battery (confirmed), track transition safety timeout reduced from 10s to 5s without evidence 10s was the problem (likely), iOS/Android native audio configuration omitted from implementation scope (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

Diagnostic logging uses a 50-event ring buffer with export capability and localStorage debug flag, capturing comprehensive context on play, error, and recovery events. The logger sits at module scope before singleton guard, ensuring it's initialized once.

Live stream EOF handling got dedicated `handleLiveStreamEnded()` with exponential backoff (2s, 3s, 4.5s, 6.75s, 10.12s, 15s max) that transitions `connectionState` to 'failed' after 6 attempts but keeps retrying. The 'ended' event handler now branches: live streams trigger reconnection, playlist streams use existing debounced transition logic.

Position watchdog runs every 5 seconds via `setInterval`, checking if `audio.currentTime` advanced at least 1 second in the last 15 seconds. When stalled, it calls `handleLiveStreamEnded()`. The timer has no stop condition and runs as long as the page is open.

Reconnection banner appears in mini-player UI during `connectionState === 'reconnecting'`, showing attempt count. CSS adds orange gradient banner above mini-player with pulsing animation. Error state subtitle changed from "Tap to retry" to "Tap ▶ to retry".

Track transition safety timeout reduced from 10 seconds to 5 seconds, with new retry logic: if `isTransitioning` flag still set after timeout, reset flag, wait 500ms, call `playStream(currentStream)` to re-resolve position if playback wanted but not active.

iOS background audio and Android audio focus explicitly deferred to manual configuration/native implementation. Implementation notes document both as NOT IMPLEMENTED with HIGH/MEDIUM impact and required steps.

## Diagnostic logging infrastructure

A 50-event ring buffer sits at module scope (lines 17-71), before the singleton guard. Each `logDiagnostic(eventType, data)` call captures: timestamp, event type, supplied data, and comprehensive context snapshot (currentStream, playback flags, connection state, retry counters, navigator.onLine, document.hidden, audio element state including src, error, networkState, readyState, position, duration).

Logging calls added at: audio 'play' event (line 596), 'playing' event (line 600), 'error' event (line 685), `play()` function (line 1224), `pause()` function (line 1237), `handleLiveStreamEnded()` (line 1058), `recoverAfterReconnect()` (line 1812).

## Live stream EOF recovery mechanism

New `handleLiveStreamEnded()` function (lines 1056-1096) handles unexpected 'ended' events on live streams. Live streams are continuous; 'ended' signals server-side socket closure or stream termination.

The 'ended' event listener (lines 658-672) now branches: if `currentStream` type is 'live', log warning, call `handleLiveStreamEnded()` if `wantsPlayback`, return early. Playlist streams continue through existing debounced `handleTrackEnded()` path.

`handleLiveStreamEnded()` guards: must have `currentStream`, stream must be type 'live', `wantsPlayback` must be true. Sets `isPlaying = false`, `isLoading = false`, increments `liveReconnectAttempts`, sets `reconnectCycleActive = true`, `connectionState = 'reconnecting'`, emits state change.

After 6 attempts: `connectionState = 'failed'`, emits state change, emits error (only on exactly 6th attempt): "Still unable to reach the stream — will keep retrying automatically."

Exponential backoff: `Math.min(2000 * Math.pow(1.5, Math.min(liveReconnectAttempts - 1, 6)), 15000)`. Attempts 1-6: 2000, 3000, 4500, 6750, 10125, 15000 ms. Attempt 7+: capped at 15000 ms.

Clears existing `reconnectTimer`, schedules new timeout. Callback guards: `currentStream` exists, stream type is 'live', `!isPlaying`, `wantsPlayback`. Calls `DarbarLiveManager.play(currentStream, true)` with `forceReload = true`.

`DarbarLiveManager.play()` modified (lines 1036-1053): new `forceReload` parameter (unused in function body but accepted). Unconditionally appends `_t=${Date.now()}` to URL (previously used 5-second bucketed timestamp). Cache-busting now uses full millisecond precision timestamp on every call, including reconnections.

**Issue 2 (MAJOR):** After 6 failures, `connectionState = 'failed'` but retry loop continues indefinitely with 15-second intervals. No maximum total retry count. No mechanism to stop. User cannot disable. If SGPC stream is permanently offline (maintenance, endpoint changed, DNS failure), device retries every 15 seconds until page closed or stream changed. Battery impact: timer wakeup + DNS lookup + TCP connect + TLS handshake every 15s.

**Issue 3 (MINOR):** User taps play button during reconnection. Mini-player's play button calls `window.AnhadAudio.play(currentStream)` → `play()` function (line 1223) → `playStream()` → `DarbarLiveManager.play()`. Simultaneously, `reconnectTimer` fires, calls `DarbarLiveManager.play()`. `reconnectTimer` cleared at start of `handleLiveStreamEnded()`, but user action and timer callback can both call `DarbarLiveManager.play()` within same event loop tick. `PlaybackQueueController.loadAndPlay()` enqueues via promise chain (serialized), but two rapid enqueues might cause: first starts loading, second aborts first (src change), first's error handler triggers another reconnect cycle. Not confirmed, but pattern is fragile.

## Position stall watchdog

`setInterval` at line 1753, 5-second interval. Closure captures `lastLivePositionCheck`, `lastLivePositionValue`, `LIVE_POSITION_STALL_THRESHOLD_MS = 15000`.

Guards: `wantsPlayback`, `isPlaying`, `currentStream` exists, stream type is 'live', audio element exists, no audio error, `readyState > 0`.

First check (when `lastLivePositionCheck === 0`): initialize both values to current time and position, return.

Subsequent checks: calculate elapsed time since last check, position delta since last value. If elapsed ≥ 15s AND delta < 1 second: log warning, log diagnostic event, reset check time to 0, call `handleLiveStreamEnded()`.

If delta ≥ 1 second: position advanced, update both check time and position value.

Watchdog detects: TCP socket open but no audio data received (position frozen), browser buffering indefinitely without firing 'waiting' or 'stalled' events, Shoutcast metadata corruption causing decoder hang without error.

**Issue 1 (MAJOR):** `setInterval` never stopped. Runs forever while page open. User plays Darbar Sahib, stream fails permanently, `connectionState = 'failed'`, user switches to Amritvela (playlist). Watchdog continues: every 5 seconds, checks guards, sees `type !== 'live'`, returns early. No functional break, but unnecessary CPU wakeup every 5 seconds forever. Worse: user closes browser tab, tab enters background (bfcache), timer keeps firing if browser doesn't suspend. Cleanup not found in stop() function, window unload handlers, or page hide handlers.

**Issue 6 (MINOR):** `lastLivePositionCheck` and `lastLivePositionValue` never reset when stream changes. User plays Darbar Sahib (live), position advances to 30 seconds. Stream stalls. User switches to another live stream (SikhNet). New stream's `currentTime` starts at 0. Next watchdog check: `lastLivePositionValue = 30`, `currentPos = 0`, `positionDelta = -30`. Delta < 1, elapsed might be < 15s (depends on timing). If elapsed ≥ 15s, triggers false positive reconnection on healthy stream. Mitigation: most stream switches happen within 15s window, so elapsed check fails and no false trigger. But pattern is fragile.

## Reconnection banner and user feedback

`overlay-player.js` modified (lines 217-231): in `updateUI()`, queries for `.gmp-reconnect-banner` element. If not found, create div, set className, insert as first child of `miniPlayerEl`. If `connectionState === 'reconnecting'`, show banner (`display: flex`), set text to "Reconnecting... Attempt ${liveReconnectAttempts}". Otherwise hide (`display: none`).

Subtitle logic (lines 237-239): if reconnecting, "Reconnecting…"; if failed, "Tap ▶ to retry"; otherwise artist name. CSS added (lines 646-676): `.gmp-reconnect-banner` positioned absolute, `top: -32px`, full width, orange gradient background, pulsing animation.

**Issue 5 (MINOR):** `reconnectBanner` variable is function-local. Every `updateUI()` call queries DOM for `.gmp-reconnect-banner`. If external code removes the banner element, next `updateUI()` creates a new one. Not a memory leak, but inefficient. Could cache reference in closure scope.

## Track transition safety timeout reduction

`handleTrackEnded()` safety timeout changed from 10000ms to 5000ms (line 1144). If `isTransitioning` still true after 5 seconds, resets flag, waits 500ms, calls `playStream(currentStream)` to re-resolve broadcast position and retry loading.

**Issue 4 (MAJOR):** No evidence 10 seconds was too long or 5 seconds is sufficient. Audit report mentions 10s safety timeout as existing safeguard against known transition hang pattern, not as identified excessive delay. Implementation notes claim "reduces user-visible gaps" but don't identify why transitions hang or whether 5s is safe threshold. If Promise chain hangs because of network delay loading next track metadata, 5s might fire before track legitimately loads, trigger retry, abort in-flight load, cause loop. Need evidence: why do transitions hang, what's safe minimum before declaring hang vs. slow load.

## Platform-specific audio configuration deferred

iOS background audio and Android audio focus explicitly deferred to manual configuration/native implementation. Implementation notes document both as NOT IMPLEMENTED with HIGH/MEDIUM impact.

iOS: requires `capacitor.config.ts` with `ios: { backgroundMode: ['audio'] }` OR Xcode configuration. Impact: HIGH. iOS suspends background audio after ~30 seconds without this.

Android: requires native Java implementation of `AudioManager.requestAudioFocus()` in `AudioForegroundService.java`. Impact: MEDIUM. Phone calls and other apps may not properly coordinate audio focus.
